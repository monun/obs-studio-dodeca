### FFmpeg 가능성 실험과 한계

2026-09-15에 로컬 FFmpeg `6.1.1-3ubuntu5`로 300~1400 Hz의 서로 다른 0.5초 시험음 12개를 생성했다. 각각 48 kHz, 스테레오 AAC, 64 kbps로 MKV에 저장하고 `-map 0:a -c copy`로 MP4에 리먹스했다.

| 결과 | MKV | MP4 |
| --- | --- | --- |
| 오디오 스트림 수 | 12 | 12 |
| 각 스트림의 채널 수 | 2 | 2 |
| 각 스트림의 읽힌 패킷 수 | 25 | 25 |
| 마지막 트랙 메타데이터 | `title=Track 12` | `handler_name=Track 12` |

이는 **FFmpeg 컨테이너 경로의 오디오 전용 실험**이다. 수정된 OBS, 영상 동기, 장시간 녹화, 네이티브 MP4 구현 또는 각 OS의 번들 의존성을 검증한 결과는 아니다. 현재 작업 환경에는 CMake·Ninja·pkg-config가 없어 OBS 빌드를 실행하지 않았다. OBS의 FFmpeg 의존성 선언은 `plugins/obs-ffmpeg/cmake/dependencies.cmake`에서 최소 6.1을 요구하며, Windows/macOS는 `CMakePresets.json`의 obs-deps를 사용한다.

재현은 `sine=frequency=<300 + 100*i>:sample_rate=48000:duration=0.5` 입력 12개에 각 `-map <i>:a:0`을 지정해 MKV를 생성하고, 아래 명령으로 리먹스·검사한다. 입력별 `title`과 `handler_name`을 `Track <i+1>`로 지정한다.

```sh
ffmpeg -i twelve.mkv -map 0:a -c copy twelve.mp4
ffprobe -v error -select_streams a -count_packets \
  -show_entries stream=index,codec_name,channels,nb_read_packets:stream_tags=title,handler_name \
  -of json twelve.mp4
```

FFmpeg는 출력 스트림마다 `avformat_new_stream()`을 생성하는 API를 제공하며, 보존할 스트림 선택은 명시적으로 다룬다. 이 API 구조, OBS 래퍼 코드, 위 실험을 근거로 **FFmpeg 라이브러리를 수정하지 않고 확장할 수 있다고 판단**한다. [FFmpeg muxing API](https://ffmpeg.org/doxygen/trunk/group__lavf__encoding.html), [FFmpeg stream selection](https://ffmpeg.org/ffmpeg.html#Stream-selection)

## Goals / Non-Goals

**Goals:**

- 트랙 개수에 의존하는 코어와 UI의 경계를 일치시키고 기존 출력 경로를 재사용한다.
- 구버전 직렬화 데이터와 신규 12트랙 데이터를 구별해 이전 처리를 한 번만 적용한다.
- 트랙 번호, 비트 위치, 인코더 슬롯, 파일 스트림 번호를 명시적으로 구분해 희소 선택과 반복 실행을 안전하게 처리한다.
- 실제 사용 경로를 검증하는 작은 테스트와 세 운영체제 통합 검증을 마련한다.

**Non-Goals:**

- 런타임 가변 트랙 수나 일반적인 오디오 그래프 재설계, 모든 출력 모드의 정책 통일.
- `MAX_AUDIO_CHANNELS`, `MAX_AV_PLANES`, 스피커 레이아웃, FFmpeg 채널 매핑의 확장.
- 추가 플러그인을 위한 구 ABI 에뮬레이션이나 구버전 OBS와의 12트랙 왕복 호환.
- 기존 테스트 전체 정비나 새로운 범용 CI·배포 시스템 구축.

## Decisions

### 1. 믹스와 출력 슬롯을 동일하게 12개로 확장한다

`MAX_AUDIO_MIXES`와 `MAX_OUTPUT_AUDIO_ENCODERS`를 12로 맞춘다. 하나의 정의를 참조하거나 컴파일 시 동등성 검사로 두 값이 어긋나지 않게 한다. 지원 비트 집합은 unsigned 연산으로 `(1u << MAX_AUDIO_MIXES) - 1u`, 즉 `0xFFF`를 사용한다. 구버전 마스크 `0x3F`는 이전 처리 전용으로 이름을 붙여 남긴다. 비트 폭을 넘지 않는 상수임을 컴파일 시 검사한다.

`obs-audio.c`, `obs-source.c`, `obs-scene.c`, `obs-source-transition.c`, `audio-io.c`, `obs-output.c`와 번들 전환·슬라이드쇼의 배열·순회·초기화 경로를 점검한다. 출력 인코더를 다루는 래퍼 배열은 출력 슬롯 상수를 기준으로 하고, 믹스 데이터를 다루는 배열은 믹스 상수를 기준으로 한다. 센티널을 찾는 인코더 열거에도 배열 상한을 명시한다.

**대안:** 상수 하나만 변경하면 출력 슬롯 부족이 남고, 두 상수만 변경하면 프런트엔드 배열 접근 오류와 잘못된 기본 배정이 남는다. 런타임 가변 배열은 현재 목표에 비해 ABI·메모리 소유권 변경이 크므로 채택하지 않는다.

### 2. 소스 저장 데이터에 확장 버전 표식을 둔다

제안하는 소스 수준 표식은 정수 `dodeca_audio_tracks_version: 1`이다. `obs_save_source()`에서 `mixers`와 함께 저장하고 `obs_load_source_type()`에서 해석한다. 장면 모음 최상위에만 두지 않아 소스 직렬화·복제·장면 가져오기에서도 적용되게 한다. 기존 `prev_ver`는 OBS API 버전으로 유지한다.

| 입력 | 로드할 배정 |
| --- | --- |
| 새 소스 생성 | `0xFFF` |
| 표식 없음 또는 현재 버전으로 인식되지 않는 표식 | 저장된 `mixers & 0x3F`; 값이 없으면 `0x3F` |
| 유효한 버전 1 표식 | 저장된 `mixers & 0xFFF`; 값이 없으면 `0xFFF` |
| 명시적 `mixers=0` | 어떤 경로에서도 0 보존 |

알 수 없는 표식은 현재 12트랙 형식으로 간주하지 않고 진단 로그를 남긴다. 현재 지원 버전으로 저장할 때에는 정규화된 배정과 버전 1을 기록한다. 이전 버전의 모니터링 자동 이전 경로도 최종적으로 동일한 구버전 배정 규칙을 따르게 한다.

일반 배정 API에는 유효한 12비트만 저장되도록 경계를 정리하고, 배정 변경 신호의 콜백이 값을 변경한 뒤에도 유효 범위를 지킨다. 알림 순서를 바꾸지 않아 UI와 번들 원격 이벤트의 기존 의미를 유지한다. 테스트에는 생성, 로드, 신호, 저장 결과의 일관성을 포함한다.

**대안:** 저장된 정수 값을 무조건 보존하면 구 OBS의 `0xFF`가 7·8번을 새로 켠다. 값이 63/255인지에 따른 추정만으로는 확장 버전의 정상 배정과 구별되지 않는다. 장면 모음 표식만으로는 개별 소스 직렬화 경로를 다루지 못한다.

### 3. 트랙 UI와 프로필 처리에 번호 기반 컬렉션을 사용한다

`OBSAdvAudioCtrl`의 `mixer1`~`mixer6` 멤버를 12개 체크박스 컬렉션으로 바꾼다. 고급 오디오 속성과 녹화·방송·VOD의 트랙 번호 선택은 1~12번을 한 행에 배치한다. 창이 좁을 때는 기존 스크롤 영역과 키보드 이동으로 모든 번호에 접근한다.

설정 화면에서는 기존 기능별 컨테이너를 유지하면서 다중 선택·단일 선택·트랙별 이름/비트레이트 위젯을 12개 컬렉션으로 생성한다. 12개 오디오 설정 페이지는 기존 탭 또는 스크롤 가능한 구조를 유지한다. `OBSBasicSettings.hpp/.cpp`, `OBSBasicSettings_Stream.cpp`, 관련 `.ui`의 생성·HookWidget·불러오기·저장·경고·메모리 추정·인코더 교체·서비스 제어 상태를 모두 해당 컬렉션으로 순회한다.

`TrackNBitrate`, `TrackNName`의 기존 키 형식을 12까지 연장한다. 1~6번 키와 사용자 값을 보존하며, 새로운 비트레이트 기본값은 `OBSBasic.cpp`의 기존 160 kbps 및 `FindClosestAvailableAudioBitrate` 규칙을 사용한다. 간단 출력은 기존 공통 비트레이트/이름 규칙을 유지한다. 신규 녹화 선택은 기존 `RecTracks=1`을 유지한다.

번호 기반 번역 키를 재사용하고 영어·한국어 기본 리소스에 7~12번 표시 및 필요한 제한 메시지를 추가한다. 기존 1~6번 번역은 보존하고 다른 로케일은 OBS의 기존 fallback을 사용한다. 100%/200% 배율과 키보드 이동에서 두 자리 번호와 모든 설정이 접근 가능한지 검증한다.

**대안:** 기존 여섯 항목을 그대로 복사해 12개로 늘리면 여러 저장·계산·경고 분기를 다시 수동 동기화해야 한다. 전면적인 설정 UI 재설계는 하지 않고 트랙 반복 부분만 정리한다.

### 4. 인코더 이름과 선택 트랙의 연결을 분리해 다룬다

`AdvancedOutput::GetAudioBitrate()`는 동적으로 `Track<N>Bitrate` 키를 생성한다. `AdvancedOutput`와 `SimpleOutput`의 인코더 초기 이름도 `std::string`과 번호 변환을 사용해 잘림을 없앤다. 간단 Opus 경로도 포함한다.

믹스 인덱스는 `OBS 트랙 번호 - 1`이고, 선택된 믹스는 오름차순으로 연속 출력 슬롯에 붙인다. 예를 들어 `{1, 7, 12}`는 믹스 `{0, 6, 11}`에서 출력 슬롯 `{0, 1, 2}`로 이어진다. FFmpeg 패킷의 `track_idx`는 출력 슬롯이며 원래 믹스 번호가 아니다.

녹화·리플레이가 비활성 상태일 때 출력의 이전 오디오 인코더 연결을 정리한 뒤 새 선택만 연결한다. 다른 활성 출력이 공유하는 인코더 자체를 중단하지 않는다. `{1..12}`에서 `{12}`로 줄인 뒤 재시작하는 시나리오가 남은 슬롯을 검출해야 한다.

**대안:** 버퍼 크기만 키우는 방식은 비트레이트 배열 범위와 이전 출력 슬롯 문제를 해결하지 않는다. 인코더를 선택 때마다 전부 파괴하는 방식은 동시 방송의 공유 수명에 영향을 줄 수 있으므로 기존 참조 관리 API를 사용한다.

### 5. 방송 선택 후보와 전송 용량을 구별한다

고급 `TrackIndex`와 `VodTrackIndex`의 유효 범위는 1~12로 확장한다. 기존 주 방송/VOD 출력 슬롯과 서비스 조건을 유지한다. `UpdateAudioSettings`, 방송 지연 추정, 서비스가 관리하는 비트레이트 UI, Multitrack Video의 주/VOD 믹스 전달까지 상위 번호를 처리한다. 간단 출력의 고정 주 믹스 1번과 VOD 2번은 그대로 둔다.

SRT/RIST는 12개 믹스 후보를 표시하되 프런트엔드의 명시적 동시 오디오 상한을 6으로 둔다. 여섯 개가 선택되면 선택되지 않은 체크박스의 추가 선택을 막는다. 외부 수정된 `StreamMultiTrackAudioMixes`는 저장/출력 시작 경계에서도 선택 수를 검사해 초과를 설명하고 실패시킨다. `AdvancedOutput`의 두 스트리밍 설정 경로에 같은 검증을 적용한다. 12믹스 배열의 크기를 줄여 제한하는 방식은 사용하지 않는다.

**대안:** `MAX_AUDIO_MIXES` 루프가 자동으로 12가 되도록 방치하면 SRT/RIST 동시 전송 수도 12로 증가한다. 방송 후보를 1~6에 고정하는 방식은 인터뷰에서 선택한 1~12번 방송·VOD 사용을 충족하지 않는다.

### 6. 기존 출력 구현을 재사용하고 경로별로 검증한다

일반 녹화의 `obs-ffmpeg-mux`와 `ffmpeg-mux` 보조 프로그램, 리플레이의 패킷·DTS 오프셋 배열, 사용자 지정 `obs-ffmpeg-output`의 믹스 순서 변환을 12개 용량에 맞춘다. 이미 상수 또는 실제 개수로 처리하는 부분은 불필요하게 다시 작성하지 않는다. MP4/MOV의 네이티브 동적 트랙 목록과 리먹스의 전체 스트림 순회도 같은 원칙을 따른다.

패킷·트랙 이름은 형식의 기존 표현을 사용한다. MKV `title`과 MP4 `handler_name`처럼 태그 이름이 달라도 사용자 트랙 이름이 보존되면 된다. AAC를 공통 수용 테스트 기준으로 사용하며, 기존 지원 조합인 Opus/MKV도 검사해 간단 Opus 이름 생성과 다중 인코더 경로를 검증한다.

일반 FLV와 간단 출력의 방송과 동일한 품질 등 단일 트랙 동작은 유지한다. 사용자 지정 FFmpeg의 리플레이 지원을 새로 추가하지 않는다. 범용 FFmpeg 설정에서 원래 불가능한 코덱·컨테이너 조합을 이번 변경의 지원 조합으로 약속하지 않는다.

**대안:** 새 muxer나 FFmpeg 포크를 도입할 근거가 없다. FFmpeg CLI만 통과시키면 OBS의 믹싱·슬롯·네이티브 MP4·리플레이 문제를 놓치므로 수용 검증은 OBS 출력물을 대상으로 한다.

### 7. 실행 가능한 검증 경로를 좁게 추가한다

`test/audio-tracks` 아래에 직렬화·믹스 배정·출력 선택을 검증하는 테스트 실행 파일과 진입점을 추가한다. 기존 프로젝트 스타일에 맞춘 opt-in CMake 옵션으로 최상위에서 연결하고 실제 등록·실행되는지 확인한다. 필요하지 않은 기존 CMocka 전체 재연결이나 새 테스트 프레임워크 도입은 하지 않는다. 테스트는 상수 값을 다시 확인하는 수준이 아니라 실제 소스 배정, 저장/로드, 부분 변경, 생성된 출력의 관찰 결과를 검사한다.

통합 검증에는 FFmpeg로 생성한 서로 다른 12개 음원과 동기 표시 영상 또는 `test/test-input`의 시험 소스를 사용한다. 내장 미디어 소스 또는 번들 시험 소스와 obs-websocket으로 반복 가능하게 구성하고, UI 확인이 필요한 부분은 같은 장면으로 수동 점검 절차를 남긴다. 외부 서비스 방송 대신 로컬 수신기 또는 출력 구성 검증을 사용한다.

| 검증 축 | 필수 사례 | 관찰값 |
| --- | --- | --- |
| 직렬화 | 구버전 0, 명시적 1·3·6, 255, 값 없음; 신규 1·7·12 저장/로드/복제 | 유효 배정, 신규 표식, 재로드 후 상위 비트 보존 |
| 실제 신호 | 12개 서로 다른 시험음, 12번 단독, 1·7·12 희소 선택, 중첩 장면·전환 | 해당 신호만 출력되고 선택하지 않은 트랙이 없음 |
| 출력 경로 | 간단 다중 녹화, 고급 MKV, 일반/Fragmented/Hybrid MP4, Hybrid MOV, 사용자 지정 AAC MKV/MP4, Opus MKV, 일반 FLV 12번 단독 | 정확한 스트림 수·오름차순·디코딩·이름 |
| 생명주기 | 녹화·리플레이 12개→1개 재시작, 반복 저장, 지원되는 일시정지·분할 | 남은 인코더 슬롯 없음, 각 파일 트랙 집합·타임스탬프 |
| 변환 | 수동·자동 MKV→MP4 | 모든 트랙·이름·오디오 내용과 시간 관계 보존 |
| 방송 | 주 12/VOD 11, 주=VOD 12, VOD 미지원, SRT/RIST 6개/7개 요청, 녹화·리플레이 동시 실행 | 선택한 믹스 전달과 기존 전송 수, 초과 오류 |
| UI/연동 | 세 OS의 100%/200% 배율, 키보드, 프로필 전환, 코덱 변경, 원격 12번 부분 변경 및 기존 6키 요청 | 번호·이름·비트레이트·용량 계산·이벤트 일치 |

생성 파일은 `ffprobe`로 스트림·채널·메타데이터·패킷을 확인하고 **각 오디오 스트림을 디코딩**해 시험 주파수·무음 구간·동기 신호를 검사한다. AAC priming과 컨테이너 시간 단위는 보정해 비교한다. 동기 합성 입력의 트랙 간 오차 기준은 한 오디오 코덱 프레임과 컨테이너 시간 단위의 합 이내로 정하고, 영상 비교에는 한 영상 프레임을 추가로 허용한다. 30분 이상 시험에서 초반·중반·후반 오차와 6트랙 기준 결과를 비교해 추가 누적 드리프트를 검출한다.

세 OS에서 공통 필수 흐름인 12트랙 MKV 녹화·리플레이·MP4 리먹스·상위 트랙 방송 선택을 실제 실행한다. 플랫폼 공통 muxer 변형은 공통 회귀 매트릭스에서 모두 검사하고, 운영체제별 사용 인코더가 다른 경우 해당 조합을 추가한다. 기존 `CMakePresets.json`과 `.github/workflows/build-project.yaml`의 Windows, macOS, Linux 빌드 구성을 사용하며 실행하지 못한 플랫폼 검증은 통과로 처리하지 않는다.

## Risks / Trade-offs

- **공개 구조체 크기·상수 계약 변경** → libobs, 프런트엔드, 모든 번들 모듈을 같은 헤더로 빌드한다. 추가 플러그인의 구 바이너리 호환을 보장하지 않는다는 범위를 문서화한다.
- **구버전의 숨은 비트가 새 배정으로 노출됨** → 소스 수준 버전 표식과 `0xFF` 회귀 사례로 이전 규칙을 고정한다.
- **두 자리 트랙 번호 및 희소 선택에서 잘못된 인코더 연결** → 동적 이름, 번호 기반 설정 키, 믹스/슬롯 구분, 12→1 재시작 검증을 적용한다.
- **메모리·CPU·파일 크기 증가** → 기존 비활성 믹스 처리 규칙을 유지하고 실제 1/6/12트랙 부하를 측정한다. `audio_output_buf`만 보면 초기화된 오디오 소스당 192 KiB에서 384 KiB로 증가하므로 추가 192 KiB가 필요하며 다른 버퍼 비용은 별도다. 전체 CPU가 정확히 두 배가 된다고 가정하지 않는다.
- **배율·로케일에 따른 UI 폭 증가** → 번호 선택의 한 행 배치를 유지하고 기존 가로 스크롤/탭 이동으로 모든 번호에 접근할 수 있는지 세 OS에서 확인한다.
- **녹화 용량 상수 확장이 방송 동시 수까지 확대** → 방송 선택 후보와 명시적 최대 동시 수를 별도로 검사한다.
- **FFmpeg 실험 결과를 모든 경로의 성공으로 오해** → 실제 OBS 생성 파일, 네이티브 MP4, 번들 라이브러리, 장시간·동시 출력 검증을 완료 조건으로 둔다.
- **편집기별 다중 트랙 표시 차이** → 파일의 신호·순서·이름과 디코딩을 수용 기준으로 삼는다. 특정 외부 편집기 지원 보장은 포함하지 않는다.

## Migration Plan

1. 구현·검증에는 기존 OBS 사용자 데이터와 분리한 테스트 프로필 및 장면 사본을 사용한다. 기존 파일을 원본 시험 데이터로 보존한다.
2. 코어·프런트엔드·번들 모듈을 일괄 빌드한다. 프로젝트가 제공하는 기존 플랫폼별 빌드 경로를 재사용한다.
3. 구버전 소스는 최초 로드에서 유효 6비트만 복원한다. 이후 정상 저장 시 버전 표식을 기록하며, 사용자가 추가한 7~12번 배정을 다음 로드부터 보존한다.
4. 프로필 키는 기존 이름을 유지하고 7~12번 기본값을 추가한다. 별도의 일괄 파일 덮어쓰기나 녹화 트랙 자동 선택은 수행하지 않는다.
5. 위 테스트 매트릭스와 세 OS 실행 검증을 완료한 뒤 변경을 완료 처리한다. 서명·설치 프로그램·게시 작업은 별도 범위다.
6. 롤백 시 기존 OBS 빌드와 변경 전 프로필·장면 사본을 사용한다. 구 OBS는 새 트랙 설정을 이해하지 못하므로 확장 버전에서 저장한 장면의 7~12번을 구 OBS를 경유해 보존하는 동작은 보장하지 않는다.
